# 云端业务数据与版本备份

## 统一旅行结构升级（2026-10-07）

旅程和足迹共用 `Trip → TripDay → ItineraryItem`。未出发/进行中的旅行在旅程页，已结束旅行在足迹页；旅程详情的“旅行记录”可在出行期间写游记。安排与回忆编辑共享地点、时间、图片及顺序，计划备注与旅行文字分别保存在 `note`、`journalNote`；不再复制收录或同步足迹。

iOS 的旧足迹模型仅作为页面适配器，不参与备份或云端上传；Android 的足迹列表由旅程即时生成，不写入本地 JSON。首次迁移先保留旧本地数据库/JSON，合并旧文字和图片，并将独立足迹转为旅行，保持已存在的安排事实。

已部署环境依次使用已执行的原子保存升级及 **`docs/cloud-unified-journeys.sql`**，无需再次初始化。统一结构脚本在事务内保存旧聚合快照到 `triptrail_unified_migration_backup`，保留旧足迹表，将云端视图改为旅行和收藏，并保护旧客户端无法覆盖新结构。脚本可重复执行，失败整体回滚；快照表不授予客户端访问权限。

双端新版在访问旅行云端前检查新字段；未升级时保留本地数据并提示升级，避免丢失旅行文字。升级后，旧足迹的云端关联根据来源旅行及云端实际 revision 迁移；未确认的关联保留，不假定旧足迹 revision 等于旅行 revision。旧版本不应继续编辑云端旅行。

验证脚本：`scripts/test_unified_journeys.mjs` 覆盖旧足迹、独立足迹、无当天归属记录、媒体和封面迁移、重复执行、原子失败回滚、过期版本冲突及旧版本写入拒绝。

地点生成只使用实际地点名称或地址；标题为空间说明，不用于补充地点。无地点/地址的安排不会生成导航点或参与规划路线。

## 初始化（本次首次开发）

在 TripTrail 数据库连接中执行完整的 docs/cloud-initialize.sql，只执行一次。
它删除旧 triptrail_cloud_records JSON 测试表和旧 RPC，在一个事务内创建关系表与备份存储。
不修改其他业务表，也不会删除 App 本机内容。不要把初始化脚本用于后续升级。全新环境初始化后还需执行 `cloud-recycle.sql`。
cloud-schema.sql 是业务部分，cloud-backups.sql 是备份部分；执行合并文件后无需再执行分文件。

业务表：triptrail_trips、triptrail_trip_days、triptrail_trip_items、triptrail_stories、
triptrail_story_days、triptrail_story_entries、triptrail_favorites，以及媒体/凭证子表。
固定字段使用标量列，关联通过外键维护；日期沿用客户端契约，以 epoch 毫秒存储。
数据库不持久化整条内容的 JSON。triptrail_cloud_records 现在是只读聚合视图，JSON 仅用于传输。
triptrail_save_record 在事务内检查版本并写入关系表；子记录失败会整体回滚。
以共同同步基准、本地修改、当前云端内容做三方比较；按实体 ID 和字段合并，仅相同字段的不同修改或删除与修改的竞争进入冲突选择。
备份表 triptrail_backups 独立于实时业务。triptrail-backups 桶存完整快照，
triptrail-media 桶存同步媒体；后续编辑实时记录不会覆盖已有备份。

## App 入口

- 旅程、足迹操作菜单，收藏长按菜单：本地内容可设为云端，云端内容不提供转回本地的入口。
- “＋”直接进入创建页；旅程与收藏页内选择普通新建或智能录入，足迹直接填写。业务内容没有手动云端导入入口。
- 我的 → 数据管理 → 导出备份：导出本地 / 上传云端。
- 恢复备份：从本地文件导入 / 从云端恢复。
- 备份管理：按服务器时间倒序列出版本，可以导出文件、恢复或删除指定版本。
- 导入分享文件：本地旅程/足迹分享文件追加到当前内容，与替换全量数据的备份恢复不同。

## 同步、离线与备份

各设备打开旅程、足迹、收藏时自动发现并下载尚未在本机的云端内容；已关联内容按版本更新。
只在打开功能/云端卡片或手动同步时拉取，导航触发有 60 秒去重，不使用定时云端轮询。
编辑后的已关联内容自动上传；离线修改保留，下次打开或同步时重试。
设为云端后保持云端模式，本地仍有离线副本。同 ID 的独立本地记录不被自动覆盖。
删除云端项目会同步删除，其他设备下次打开相应功能或手动同步时移除本地副本。离线删除先保存队列，联网后补交，不会再次下载。

“我的 → 数据管理 → 回收站”可恢复一天内删除的旅程、足迹、收藏；云端回收站公开共享。本地项目仅在本机恢复。云端保留期以服务器收到删除时开始计算，重复提交不会延期。恢复后其他设备下次同步自动加载。

现有数据库执行 `docs/cloud-recycle.sql` 增量迁移。超过 24 小时服务器拒绝恢复；关系数据在访问回收站时清理，保留最小删除标记防止离线旧版本重新上传。共享媒体对象不自动删除，可通过数据管理手动检查闲置文件。恢复云端备份仍由用户显式选择版本。
本次重建使用新同步绑定命名空间，旧测试记录的本地副本变为本地模式，可重新主动上传。

完整备份复用两端现有 .triptrailbackup 格式，包含可读取的图片/视频。
资源无法读取时先提示取消或跳过。云端以 8 MiB 分块传输，避免一次读入整个视频备份；
版本表记录总字节、分块数量、SHA-256、完成状态。所有分块上传完成才标记 ready。
下载后验证总大小和哈希，通过后才进入恢复确认。恢复前等待当前同步完成，
成功后清除旧同步绑定，恢复内容作为本地副本，不会把历史快照自动覆盖回共享云端。
上传/删除中断的版本在列表可见，可以重试删除；删除先标记 deleting，再删除分块，最后删除元数据。
删除备份不删除当前业务内容。本地文件由系统文件选择器管理，App 不擅自删除用户文件。

旧同步媒体不自动垃圾回收；数据管理提供“清理云端闲置文件”，预览并经用户确认后通过 Storage API 删除。
初始化脚本不直接删除 Storage 元数据，避免产生无法追踪的物理对象。

### 手动清理云端闲置文件

先在现有数据库执行 `docs/cloud-cleanup.sql`（须已部署关系表、备份表和回收站迁移）。脚本可重复执行，不清空业务数据，也不注册定时任务。双端更新后入口位于“数据管理 → 清理云端闲置文件”，回收站仍在最后。

- 检查阶段只登记候选并列出类型/数量，不删除文件，不清理回收站记录。
- 对象最近创建/更新时间超过 7 天，且两次无引用检查间隔至少 24 小时，才允许进入确认名单；首次扫描可能显示无可清理文件。
- 全部四张媒体表均检查引用，包括其他旅程、足迹封面、收藏和尚未被回收站清理的记录。
- 所有现存备份版本（含未完成、正在删除）都保护其文件；只清理没有任何版本记录的备份残留，不自动删除用户备份。
- 每次最多处理 100 个对象；弹窗确认后再次核对引用。取消不会退役路径或删除对象。
- SQL 通过统一事务锁将媒体引用写入与清理认领串行化。认领后的路径永久退役，防止离线旧客户端在物理删除期间重新引用。
- 文件始终通过 Storage DELETE API 删除，SQL 不直接删除 `storage.objects`。失败/退出后可重新检查重试；界面不将部分失败报告成全部成功。
- 客户端复用缓存路径前检查对象存在且未退役；新上传使用随机 UUID 目录。竞争期间保存被拒绝时本地数据仍保留，下次同步使用新路径重新上传。
- 退役路径标记保留，防止旧客户端复活引用；该功能不保证回收这些保护性元数据。执行 SQL 前，入口会提示功能尚未启用。

验证：`PGLITE_MODULE=/tmp/triptrail-pgcheck/node_modules/@electric-sql/pglite/dist/index.js node scripts/test_cloud_cleanup.mjs`。测试仅使用隔离内存数据库，不操作线上资源。

## 主动、单项与原子保存（2026-10-07）

先在现有云端库执行 `cloud-atomic-save.sql`（不要重新执行初始化脚本）。该脚本可重复执行，兼容已有回收站与媒体清理保护。客户端编辑安排或足迹记录点击保存时，将当前实体合入已加载的基准快照，保留其他实体；已有云端绑定缺少基准快照时，先重新加载再保存。新建云端项目仍使用创建 RPC。

打开页面、关闭编辑弹窗、切换标签、网络恢复只允许拉取与检测冲突，不上传未提交的数据。沿用各编辑器已有的“保存”：单条安排只提交该安排，当天与旅程信息只提交对应元数据，不带入其他未提交修改。各功能菜单不额外提供整项目保存或常驻重新加载入口。数据库版本比较、修改行的 upsert、删除被移除的实体在同一事务内完成，版本不匹配或媒体非法会整体回滚。未改动的子实体不会删除重建。

无冲突的云端变化直接合并，且不触发被动上传。真正冲突时保留本地并提供“重新加载（使用云端）”与“冲突内容使用本地”；版本选择仅作用于冲突字段，双方其他修改均保留。编辑保存产生的冲突在用户选择后继续提交该次保存范围；后台检测产生的冲突只更新本地合并结果，后续由编辑器保存提交。自动结束归档只提交新生成的对应足迹，不顺带提交其他旅程。

本地验证：`PGLITE_MODULE=/private/tmp/triptrail-pgcheck/node_modules/@electric-sql/pglite/dist/index.js node scripts/test_cloud_schema.mjs`，覆盖重复迁移、未改媒体行保持、过期版本拒绝、失败回滚、删除恢复与级联清理。

自动根据时间变化的进行中/已完成状态不视为用户内容修改；有时间待定的手动完成状态仍参与变更检测。旧安装的绑定缺少基准快照时保守保留本地并要求重新加载，避免推断后覆盖云端。

三方合并在客户端完成；数据库继续使用已部署的 `triptrail_patch_record` 版本 CAS 和事务，无需为此再次执行 SQL。提交期间遇到版本竞争会重新读取并比较，最多重试两次。媒体按稳定 ID 合并，设备文件路径及自动安排状态不参与用户修改判断；云端内容按实际模型格式归一化后建立基准，避免缺省字段误判为本地修改。

保存安排 A 后，其他尚未提交安排 B 的真正冲突仍保留其共同祖先；不会因为旅程版本号已推进，就把 B 的本地修改当成无冲突更新覆盖云端。再次保存 B 时仍要求用户选择冲突内容。该基准随绑定持久化，重启后仍可比较。
